# U16: parent-session skill load (C4 baseline)

Date: 2026-10-24
Baseline commit: `cd8ecac`
Pi version: 0.84.2 (the version pinned by `package-lock.json`)
Scope: measurement and documentation only. No runtime, profile, skill or plugin
change. C4 remains open.

## Question

After `pi install .`, how many skills does a main Pi session discover, how large
are the descriptions it receives, where do they come from, are there duplicates,
and would profile filtering change anything useful? Parent discovery is measured
separately from child-session injection. Context-file duplication is not part of
this report.

## Environment and method

The run used a disposable `HOME`, a disposable Pi agent directory and a neutral
empty project directory, so the personal Pi installation, its settings, its
global skills and every consumer project stayed untouched. `pi install .` was
executed with the repository itself as the local package.

The measurement script is
[`measure.mjs`](measure.mjs). It uses Pi's own `DefaultResourceLoader`, then
builds the base main-session system prompt through `createAgentSession` /
`SessionManager.inMemory()`. The session is never prompted, so no
`before_agent_start` turn hook runs and no model request, token usage or cost is
produced. Discovery was independently confirmed through the real CLI in RPC mode
(`get_commands`).

```bash
REPO=/path/to/agent-brains
TMP=$(mktemp -d)
mkdir -p "$TMP/home" "$TMP/agent" "$TMP/neutral-project"
export HOME="$TMP/home"
export PI_CODING_AGENT_DIR="$TMP/agent"
export PI_OFFLINE=1

node "$REPO/node_modules/@earendil-works/pi-coding-agent/dist/cli.js" --version
# 0.84.2

node "$REPO/node_modules/@earendil-works/pi-coding-agent/dist/cli.js" install "$REPO"
node "$REPO/docs/evals/pi-skill-load/measure.mjs" \
  "$TMP/neutral-project" "$TMP/agent" > "$TMP/results.json"

# Independent CLI observation: skill commands and their description payload.
# Run it from the neutral project explicitly, never from the repository root.
(
  cd "$TMP/neutral-project"
  printf '%s\n' '{"type":"get_commands","id":"u16"}' |
    node "$REPO/node_modules/@earendil-works/pi-coding-agent/dist/cli.js" \
      --mode rpc --offline --no-session > "$TMP/rpc.jsonl"
)
```

The CLI observation returned 64 `skill:*` commands with 18,676 bytes of
descriptions, matching the loader. The prompt measurement returned 59 rendered
`<skill>` entries and the exact skills block generated by `formatSkillsForPrompt`.

The script prints one JSON document and does not prompt the model, but the Pi
SDK it loads is not side-effect free. On the recorded run `pi install` wrote
`$TMP/agent/settings.json`, and the measurement created
`$TMP/agent/auth.json` and `$TMP/agent/models-store.json` (both `{}`). All three
files stayed inside the disposable agent directory; `git status --short` showed
no new files in the repository after the neutral, symlink and copy runs. This is
why the agent directory is mandatory: without the second argument or
`PI_CODING_AGENT_DIR`, `measure.mjs` exits with status 2 before loading the SDK.
Resolving an empty agent-dir path would otherwise point the SDK at the
repository root and create `auth.json`/`models-store.json` there.

All figures below are characters or UTF-8 bytes. No token count was measured or
inferred: bytes and characters are not tokens. The parent prompt and skills block
also contain absolute `<location>` paths, so their byte size changes with the
repository or consumer path length.

### Origin and duplicates

Every discovered skill came from the installed package manifest
`pi.skills: ["./.agents/skills"]`, i.e. `origin: package`, `scope: user`.
The isolated agent directory had no user or project skills, and the neutral
project had no `.pi` or `.agents` directory. Diagnostics were empty, no skill
name collided, and no two visible skills had byte-identical descriptions.

Two controlled project-local variants were measured in separate consumer
directories, using `PI_U16_APPROVE_PROJECT=1` so the project was treated as
trusted:

| Variant | Discovered / visible | Description bytes | Collisions | Result |
|---|---:|---:|---:|---|
| Neutral project | 64 / 59 | 17,706 | 0 | package only |
| `.agents/skills` symlink to the store | 64 / 59 | 17,706 | 0 | project source wins; same canonical files |
| independent copy of `.agents/skills` | 64 / 59 | 17,706 | 64 | project copy wins; each package name is a collision |

Copies therefore do not increase the number of rendered skills: Pi resolves the
same name once. They change which revision wins, and a stale copy can silently
shadow newer package descriptions. The symlink/copy runs produced a larger raw
block (31,885 bytes on the recorded paths) with identical skill and description
sets; the difference is attributable to their longer temporary `<location>`
paths.

The complete preparation and collision check is reproducible from the same
isolated environment. The symlink points at the canonical store; the copy is a
fully independent snapshot:

```bash
SYMLINK_PROJECT="$TMP/project-symlink"
mkdir -p "$SYMLINK_PROJECT/.agents"
ln -s "$REPO/.agents/skills" "$SYMLINK_PROJECT/.agents/skills"

COPY_PROJECT="$TMP/project-copy"
mkdir -p "$COPY_PROJECT/.agents"
cp -R "$REPO/.agents/skills" "$COPY_PROJECT/.agents/skills"

for NAME in symlink copy; do
  PI_U16_APPROVE_PROJECT=1 node "$REPO/docs/evals/pi-skill-load/measure.mjs" \
    "$TMP/project-$NAME" "$TMP/agent" > "$TMP/results-$NAME.json"
done

# Both trees contain 64 SKILL.md files; -L is required for the symlinked tree.
find -L "$SYMLINK_PROJECT/.agents/skills" -name SKILL.md | wc -l
find "$COPY_PROJECT/.agents/skills" -name SKILL.md | wc -l

# Collision evidence comes from Pi's loader diagnostics, not from the file count.
for NAME in symlink copy; do
  node -e '
    const fs = require("node:fs");
    const result = JSON.parse(fs.readFileSync(process.argv[1], "utf8"));
    const collisions = result.parent.diagnostics.filter((d) => d.type === "collision");
    console.log(JSON.stringify({
      project: result.runtime.cwd,
      discovered: result.parent.discoveredSkills,
      visible: result.parent.promptVisibleSkills,
      collisions: collisions.length,
      duplicateDescriptions: result.parent.duplicateDescriptions.length,
    }));
  ' "$TMP/results-$NAME.json"
done
```

The symlink run reports `discovered: 64`, `visible: 59`, `collisions: 0`; the
independent copy reports the same counts with `collisions: 64`, one per package
skill name, and its project copy wins every collision. Neither run has duplicate
descriptions. Raw block bytes depend on the temporary paths and are therefore
not expected to equal the recorded 31,885 exactly.

## Profile filtering: static projection

Profiles are not applied to the parent today. The table projects what would
happen if the parent discovered only the skills listed by each profile, using the
runtime descriptions and the profile manifests. The projected block includes the
per-skill `<location>` overhead. These are static projections, not a runtime
after a profile change.

| Profile | Visible skills | Description bytes | Share of all descriptions | Projected block bytes | Block reduction |
|---|---:|---:|---:|---:|---:|
| `common` | 24 | 5,279 | 29.8% | 10,201 | 65.4% |
| `nodejs` | 26 | 5,710 | 32.2% | 11,036 | 62.6% |
| `nodejs-ai-backend` | 31 | 7,672 | 43.3% | 13,916 | 52.9% |
| `nextjs` | 40 | 10,774 | 60.8% | 18,909 | 36.0% |
| `laravel` | 34 | 9,338 | 52.7% | 16,265 | 44.9% |
| `laravel-analytics` | 41 | 11,893 | 67.2% | 20,203 | 31.6% |
| `astro` | 32 | 7,781 | 43.9% | 14,281 | 51.6% |
| `frontend` | 34 | 8,939 | 50.5% | 15,887 | 46.2% |
| `full` | 56 | 16,881 | 95.3% | 28,158 | 4.6% |

`measure.mjs` emits the last two columns directly as
`profiles[].projectedSkillBlockBytes` and `profiles[].blockReductionPercent`.
The projected block is generated with `formatSkillsForPrompt(matchedVisibleSkills)`,
so the table can be reproduced from the script output without a second
calculation.

For a single-stack project, filtering the parent to that stack's profile would
remove roughly half to two thirds of the skills block. `full` is not a useful
filter (4.6%). The reduction is real in bytes, but it removes capabilities
rather than deduplicating them, assumes the project stack is known and stable,
and would make cross-stack work in the same session fall back to unavailable
skills. No cost, latency or quality effect was measured.

## Child-session injection (kept separate)

Children do not inherit the parent's 64-skill discovery unfiltered:
`skillsOverride` keeps only the role/profile selection. The numbers below are
derived from the runtime skill descriptions plus the repository's
`selectSkills`; the skills block is exactly what Pi would render. They do not
include the context files added through `agentsFilesOverride`, which belong to
S1/S2.

| Stack profile | Role | Selected | Rendered | Description bytes | Skill block |
|---|---|---:|---:|---:|---:|
| `nodejs` | planner | 13 | 12 | 2,361 | 5,070 |
| `nodejs` | developer | 12 | 12 | 2,203 | 4,928 |
| `nodejs` | reviewer | 12 | 12 | 2,461 | 5,173 |
| `nodejs` | tester | 2 | 2 | 305 | 1,055 |
| `nextjs` | planner | 25 | 24 | 7,037 | 12,119 |
| `nextjs` | developer | 25 | 25 | 7,083 | 12,367 |
| `nextjs` | reviewer | 25 | 25 | 7,321 | 12,656 |
| `nextjs` | tester | 9 | 9 | 2,915 | 5,019 |

Selected-but-hidden entries explain the difference between selected and
rendered counts (`to-spec`, `review-animations`). The child skill block is
1.1–12.7 KB in these examples versus 29.5 KB in the parent.

One routing observation surfaced while separating the measurements:
`solution-capture` is selected for planner, developer, reviewer and
security-reviewer children in every sampled profile. It is absent from
`SKILL_CATEGORIES`, so it falls through to the permissive `craft` default even
though the profile comments describe it as an explicit workflow skill. That is
a child-injection candidate for C5/S1 review, not a U16 change; its presence was
not evaluated for quality.

## Limits

- No live interactive TUI session and no provider request. The base parent prompt
  was built by the Pi 0.84.2 SDK from the same resource loader, before any
  `before_agent_start` extension hook; CLI RPC independently confirmed discovery
  and description totals.
- The isolated home deliberately excludes personal `~/.agents/skills`,
  `~/.pi/agent/skills`, project `AGENTS.md` files and project context. A real
  machine or consumer project can load more than this baseline.
- No token count, billed cost or latency was measured. Any token conversion needs
  the target model's tokenizer and a real request.
- Profile rows are static projections from manifests, not post-filter runtime
  measurements. They say nothing about task quality or skill usefulness.
- Only exact duplicate descriptions and Pi name collisions were checked;
  semantic overlap between skills was not measured.
- The byte size of the prompt and skills block depends on absolute
  `<location>` path lengths. Counts and description totals are stable; block and
  prompt totals are tied to the recorded paths.
- Child context-file injection and parent/child context-file duplication remain
  unmeasured here. They are S1/S2 work.

## Recommendation

Measure before optimizing, and do not fold profile filtering into this step.
The parent load is material: 59 rendered skills, a 29.5 KB skills block and
91.6% of the isolated parent prompt. The largest safe-looking lever is
single-stack profile filtering (62.6% block reduction for `nodejs`), but it
removes capabilities and has no measured quality or cost benefit; `full` barely
helps. Exact duplicates are not the cause in the isolated baseline, and a
discovered-versus-injected context-file comparison is still missing.

Next step toward S2: capture provider/model, input/output tokens, cache-read and
cache-write usage, exposed cost and elapsed time through run logs and resume,
distinguishing unavailable from zero cost and provider-reported cost from
subscription billing. Record representative multi-file exploration tasks, then
compare total cost and latency before and after any S1 deduplication. C4 stays
open until that baseline and the S1 comparison exist; S1, S2 and S3 are not
implemented by this report.
