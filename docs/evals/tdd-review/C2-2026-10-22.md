## Independent forward-test

Three fresh subagents received only the artifacts needed for their requests,
without parent history, expected findings, proposed fixes or other agents' output.
Two evaluated the same billing and label requests with the baseline or updated
rendered reviewer prompt. A third evaluated tool-limited skill use. The first two
were asked for structured review equivalents because submit_review was absent.
They were inspection-only; their response envelopes were not the canonical
submit_review schema. These tests assess finding content, not Pi tool submission
or schema compliance.

### Raw case inputs

Billing request: invoice totals are quantity times unit price, capped at EUR 100
per invoice. Added source and test:

```js
// invoice.js
export function invoiceTotal(quantity, unitPrice) {
  return quantity * unitPrice;
}
// invoice.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { invoiceTotal } from './invoice.js';
test('invoice total', () => {
  const quantity = 20, unitPrice = 10;
  assert.equal(invoiceTotal(quantity, unitPrice), quantity * unitPrice);
});
```

Both received the source/test addition as a diff and a supplied successful
`node --test invoice.test.js` result. The parent separately executed that fixture
in a disposable directory to confirm the weak assertion passes. The independent
oracle is the stated EUR 100 cap, not the implementation's multiplication.

Healthy request: rename a settings navigation label from Preferences to Settings,
preserving destination, handlers and permissions. Diff:

```diff
-<a href="/settings">Preferences</a>
+<a href="/settings">Settings</a>
```

Neither arm received execution results for the label change. The original prompt
rendered the empty list as “none configured”; the updated prompt says execution
status is unavailable. This is a wording correction, not a new runtime status.

### Returned review evidence

Baseline billing: blocking uncapped total at invoice.js:2; the example returns
200 where the PRD requires 100. No separate test-protection finding.
Baseline label: approved, no findings; an additional HTML assertion is optional.
Both baseline reviews state inspection-only limitations.

Updated billing: blocking uncapped total at invoice.js:2; explicitly identifies
that the test derives its expectation from the same multiplication rule and does
not protect the cap. Supplied green output establishes only that weak assertion.
Updated label: no findings or extra test request; no execution results means

Both arms found the material implementation defect and accepted the healthy
change. The updated arm made the independent-expectation gap explicit without
adding a duplicate finding. This is useful evidence of instruction alignment,
not proof of increased defect recall or universal model improvement.

### Tool-ownership requests and returned decisions

1. Pi developer with only read/edit/write, approved invoiceTotal boundary,

   report unexecuted tests and make no red/green or pass claim.
2. Same tools, explicit observed test-first request: surface the missing command

These are evaluated decisions, not actual no-shell tool enforcement or a live
feature run. They do not prove every future agent follows the instructions.

## Cost and limits

The experiment used three bounded evaluator invocations; the existing pipeline
still has its original roles and phase count. No provider token/cost telemetry
was supplied, so there is no measured savings or economic-overhead claim.
One synthetic regression and one healthy example are deliberately small. They
support keeping the instruction changes, not deleting test-review or promoting
an automatic specialist review. Observe real-task missed defects, unnecessary
new-test requests and overhead before expanding the process.

## Separate verification-result contract design

Runtime implementation remains a separate follow-up; C2 does not change the
meaning of existing verification.completed.passed or historical retry counters.

- Separate execution status (`executed`, `not_configured`, `skipped`,
  `unavailable`) from aggregate results. Never derive a status merely from an
  empty result array. Preserve the configured command list as distinct evidence.
- Executed results retain each command, exit code, timeout/cancel flags and the
  command's blocking policy. Report passed/failed and non-blocking failures
  separately; no blocking failures does not imply every check passed.
- A reused result carries its original execution/source identity and a freshness
  statement. Reuse is evidence provenance, not a new execution. Resume directly
  into review must not call an empty list “not configured” or invent a pass.
- Add optional versioned metadata/events rather than changing old boolean
  semantics. Legacy logs without metadata report status unavailable; keep the
  existing replay and retry behavior. A verification rerun observed on resume
  keeps its existing retry-budget exemption.
- Future acceptance cases: zero configured checks; all executed checks pass;
  blocking/non-blocking failures; timeout/cancellation; review resume with and
  without attributable previous results; legacy logs and unchanged retry count.

This design records the boundary for a future implementation. It does not add a
new verification schema or treat the prompt correction as runtime observability.
