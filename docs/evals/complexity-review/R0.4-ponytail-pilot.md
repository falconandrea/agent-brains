## Methodology

Ten read-only evaluator runs of record: `ponytail-review`, `karpathy-guidelines`
and `simplify` ran once per diff (six single-lens runs), and `code-review` was
executed faithfully per its own contract — two separate parallel sub-agents
(Standards axis, Spec axis) per diff (four axis runs). Each run was a
fresh-context subagent that received only its own lens skill, the diff range, and
a hard read-only mandate (no file writes, no mutating git commands, no formatters,
no test runs). The six single-lens runs were explicitly forbidden to read the
other lenses' skills and `docs/evals/**`, and predate this report. The four
faithful code-review axis runs postdate the report but their prompts contained
only the diff command, commit list, standards/spec sources and the skill's brief
— they were **not** explicitly forbidden from reading R0.4 artifacts in the
working tree, so contamination cannot be categorically excluded; what can be
said is that **no R0.4 content is visible in their returned outputs** (all four
are preserved verbatim and inspectable). The `code-review` lens was
initially executed as a single-context proxy (both axes in one run, contrary to
the skill's two-sub-agent contract); that proxy run is preserved but superseded —
see [runs/README.md](runs/README.md).

**Fixture state disclosure.** All runs executed against the repository at HEAD
`763387a` **with the untracked pilot skill `extra/skills/ponytail-review/`
present in the working tree** — necessarily, because the ponytail lens reads the
skill under test. The six single-lens runs (and the superseded proxy runs) were
explicitly forbidden from reading it; the four faithful code-review rerun prompts
contained no such prohibition — see Methodology. The reviewed
diffs come from commit objects, so the untracked folder could not alter them;
this is recorded because "fixture = clean HEAD" would be false.

**Run artifacts.** The exact prompt and the complete verbatim output of every run,
plus the shared configuration snapshot (fixture repository and state, runtime,
provider, read-only mandate, limitations), are preserved under
[runs/](runs/README.md). Under the evaluation-evidence standard in
[docs/evals/agent-workflows/README.md](../agent-workflows/README.md) (raw session
export plus configuration snapshot beside the summary, never the summary alone)
this is **substantial evidence with a documented limitation, not a fully
reproducible configuration**: prompts and verbatim outputs are complete, but the
exact per-run model variant and the tool-call transcripts were not exported (see
[runs/README.md](runs/README.md) for the classification and the recorded remedy).

None of the findings were applied. The R0.4 work products are: the new skill,
this report, its run artifacts, the structural tests and the roadmap update. The
working tree also contains unrelated untracked user files and directories that
appeared during/after the session (observed: `docs/research/pi-ecosystem-followup-assessment.md`,
`docs/research/dynamic-harness-and-seo-integration-assessment.md`,
`docs/audits/`) — none created by this work, none referenced by any run, and all
to be excluded from any staging of R0.4 changes (untracked status guarantees
exclusion from a staged R0.4 diff, not intactness against any baseline).

## Explicit invocation path

Verified against the official docs on 2026-09-21 (Codex:
[Build skills](https://learn.chatgpt.com/docs/build-skills); OpenCode:
[Agent Skills](https://opencode.ai/docs/skills)) and against this machine:

- **Verified (structurally tested):** the skill is absent from every auto-load
  surface of the repository — Pi (`package.json` `pi.skills` loads only
  `./.agents/skills`), all `profiles/*.list`, `src/skill-router.ts`, `setup.sh`
  — and from the canonical store `.agents/skills/` itself.
- **Codex (documented path, per official docs):** local skills load from
  repo scope (`$CWD/.agents/skills` up to the repo root), user scope
  **`$HOME/.agents/skills`**, admin (`/etc/codex/skills`) and system;
  **symlinked skill folders are supported and followed**. Manual install:
  symlink `extra/skills/ponytail-review/` into `$HOME/.agents/skills/` (or into
  a consuming project's `.agents/skills/`), then invoke `$ponytail-review`.
  `agents/openai.yaml` `allow_implicit_invocation: false` is the Codex-side
  guard: Codex will not implicitly invoke it, while explicit `$` invocation
  still works. Local check: `$HOME/.agents/skills` exists on this machine with
  personal skills in it; `ponytail-review` is not among them — the skill is
  dormant. (Doc discrepancy recorded: the bundled skill-creator guide still
  points at `$CODEX_HOME/skills`; the official location table above does not
  list it and takes precedence.)
- **OpenCode (documented path, per official docs):** skills load from
  `.opencode/skills/`, `.claude/skills/`, `.agents/skills/` (project, walking up
  to the worktree) and `~/.config/opencode/skills/`, `~/.claude/skills/`,
  `~/.agents/skills/` (global), or explicit `skills` config entries (V2).
  `agents/openai.yaml` has no effect on OpenCode, and unknown frontmatter fields
  are ignored (so the legacy `disable-model-invocation` key used by older repo
  skills is not a recognized guard). The explicit-only mechanism differs by
  major version:
  - **V2** documents `metadata.opencode/autoinvoke: false` in `SKILL.md`
    frontmatter: the skill is omitted from the model's available list but
    "remains registered and can still be loaded explicitly by ID" — the only
    documented OpenCode mechanism that is genuinely *user-invocation-only*.
    **The pilot skill now carries this key itself** (added during review
    iteration; structurally asserted by `tests/extra-skills.test.ts`), so an
    install under OpenCode V2 is explicit-only by the skill's own frontmatter
    with no extra configuration.
  - **V1** (fetched docs list only `permission.skill` rules): `ask` advertises
    the skill and prompts for approval, but the model can still initiate the
    load — **approval-gated, not explicit-only**; `deny` hides it and rejects
    loading entirely, **including explicit invocation** — disabled, not
    explicit-only. On V1 there is therefore *no* permission value that yields
    "only the user can invoke it".
  - The machine used for this pilot runs OpenCode **1.18.31 (V1)**, so in the
    current local environment the skill can at best be approval-gated (`ask`)
    or disabled (`deny`); true explicit-only in OpenCode requires V2's
    `autoinvoke: false`.
- **Consequence:** "explicit-only" currently means *not installed anywhere*;
  when installed, it is enforced by the skill's own files in both tools —
  `agents/openai.yaml` `allow_implicit_invocation: false` in Codex and
  `metadata.opencode/autoinvoke: false` in OpenCode V2 (ignored, harmlessly, by
  the locally installed V1, where only approval-gated `ask` or disabling `deny`
  are reachable). A live invocation check in either tool remains an open
  follow-up before any promotion beyond the pilot.

## Conclusion

**Promotion criterion** — "at least one genuinely actionable deletion, reuse,
stdlib/native replacement or YAGNI finding across the two diffs that is not merely a
duplicate correctness, security or spec finding" — is **met, twice over**: A-PT1
(`--adr-dir` YAGNI deletion, actionable, ~9 lines, independently confirmed by
karpathy and by the faithful Standards axis' Speculative Generality finding
A-CR-S4 — all three resolve by deletion), and B-PT1 (an actionable `reuse` finding
with a named replacement that is unique among findings of record).

**Decision options considered:**

1. keep `ponytail-review` as an explicit standalone skill;
2. add a separately reported Complexity axis to local `code-review`;
3. reject or defer.

**Decision: option 1 — keep `ponytail-review` as an explicit, standalone,
explicit-only skill under `extra/skills/`.** It contributed one strictly unique
actionable finding among the records of this pilot (B-PT1, reuse with named
replacement) plus a deletion-first ladder, a directional net-line budget and
assumption-gated `needs-confirmation` reporting that the local lenses lack, and
it held its scope and safety boundaries on both an implementation-heavy and a
prose-heavy diff. That said, most of its findings overlapped with
`karpathy-guidelines` and `simplify`, so merging it into `code-review` now
(option 2) is premature: the two-axis review's value depends on keeping its axes
few and distinct. In the review workflow, place it as an **optional pass after
Standards/Spec** when a substantial diff introduces abstractions, configuration,
dependencies, refactors or significant code volume; skip it by default for small
or documentation-only reviews. Revisit default integration after further real
use — including at least one live-verified explicit invocation — at which point
the merge remains the recorded fallback.

**`ponytail-audit`: deliberately omitted.** The pilot established no distinct,
concrete need for whole-repository complexity analysis: both evaluations were diff
reviews, no whole-repo question arose that the diff-review skill could not serve,
and repo-wide architectural surveys are already covered locally by
`improve-codebase-architecture`. Adding it would expand pilot surface without
evidence.

**No suggested changes were applied.** All findings remain unapplied, across
both the findings of record and the superseded proxy run (whose since-withdrawn
"keep and stricten" resolution for `--adr-dir` is preserved only in its
artifact).
